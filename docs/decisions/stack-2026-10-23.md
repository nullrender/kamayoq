# App stack (decision of 23/10/2026)

Decided after a general review of the project on 22/10/2026 and a report comparing four stack options. Desktop is out: the focus is only Android phones and tablets; if desktop ever happens, it gets decided then.

## What is decided
- **Language and UI:** Kotlin + Jetpack Compose, Android only (phone and tablet).
- **Core** (`core`): Kotlin with no Android classes at all; runs and is tested on the PC's JVM; a CI test fails if Android gets in. This is not preparation for desktop; it is about testability and discipline.
- **Text reader:** foliate-js, our own fork in `third_party/foliate-js`, based on Readest's fork (MIT), with the origin commit and every change recorded; runs in the system WebView. Before the first reader: blocking of the book's scripts (CSP) and a minimal-reach bridge, tested with a deliberately malicious EPUB.
- **Image reader:** native. Compose, conditional on the test on a test tablet; if it stutters where Views does not, a Views component (as Mihon does) inside the Compose screen.
- **Database:** SQLite via SQLDelight (explicit SQL, migrations verified at build time, data-preservation tests mandatory).
- **Files:** only through the Storage Access Framework (folder chosen by the user). Read access is enough to import and read; write access only when the person turns on the metadata file next to the work, requested at that moment. The app never changes the work's files.
- **License:** GPL-3.0-or-later. **Distribution:** only GitHub and F-Droid; no proprietary dependencies.
- **Language:** English as the source, pt-BR alongside, in the same commit.
- **Extensions (phase 2):** our own ecosystem, probably in JavaScript, with Mihon's extensions and LNReader's plugins as code references. The test of running Mihon extensions through a dex virtual machine (dexvm) is no longer needed.
- **Build and install:** GitHub Actions builds the APK, installed on the test phone. Our own signing key, generated and kept outside git; the key used in the earlier proofs of concept is treated as exposed and is removed from the configuration.

## What is not decided now
Desktop (Linux, Windows) and iPhone: nothing is prepared beyond the Android-free core. Kotlin Multiplatform and Compose Multiplatform were not chosen. Name and identifier: next decision, before the skeleton (see `name-and-identifier-2026-10-24.md`). The progress data model, the folder convention and the exact scope of the first skeleton get their own decisions (see `progress-contract-2026-10-24.md` and `folder-convention-2026-10-24.md`).

## Why (summary)
Android is the platform where reading happens; both readers are strong on this stack (native images, text in the WebView with pt-BR hyphenation measured on the test phone); there is more open reference code for writing and reviewing (Mihon, Apache-2.0); publishing on F-Droid is trivial. Two arguments from the original proposal do not hold: "only Kotlin can load Mihon extensions" (Mangayomi, in Flutter, does it through a bridge) and "serious apps use Kotlin" (it does not prove superiority). The honest justification is the smaller one: fewer bridges to Android and more reference code.
